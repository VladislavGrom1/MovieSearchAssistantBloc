# 0004. Эндпоинт поиска выбирается по ключевому слову, а не по отсутствию фильтров

- **Статус:** Принято (закрывает регрессию «Показать» без фильтров)
- **Дата:** 2026-11-13

## Контекст

`SearchedFilmsBloc` обслуживает два разных входа: ручной поиск со строкой (`SearchFilmScreen` → `SearchedFilmsRoute(keyword: ...)`) и экран фильтров (`FilterFilmScreen` → `SearchedFilmsRoute(countries/genres/yearFrom/yearTo)`). Оба приходят одним событием `LoadSearchedFilms`, поэтому BLoC сам решает, какой эндпоинт звать:

- `GET /api/v2.1/films/search-by-keyword` — только поиск по строке, `keyword` обязателен и уходит в запросе всегда;
- `GET /api/v2.2/films` — фильтры; без единого параметра отдаёт подборку.

После подключения keyword-поиска (ADR [0003](0003-search-by-keyword-year-is-string.md)) развилка была написана «нет фильтров → значит, это поиск по строке»: `if (countries == null && genres == null && yearFrom == null && yearTo == null)`. Для экрана фильтров с невыбранными фильтрами это давало `search-by-keyword` с `keyword: ''` — валидный запрос без совпадений, экран показывал «Фильмы по запросу не найдены» вместо подборки, которая была до регрессии.

Варианты:

1. Считать признаком keyword-поиска непустое ключевое слово.
2. Передавать в событии явный флаг `searchMode`, выставленный экраном.
3. Завести отдельные события на каждый вход (`SearchByKeyword`, `SearchByFilters`).

## Решение

Вариант 1. [`searched_films_bloc.dart`](../../lib/presentation/bloc/searched_films/searched_films_bloc.dart:124) вычисляет `keyword` (trim), приводит пустые списки стран и жанров к `null` и идёт в v2.1 только при `keyword.isNotEmpty && !hasFilters`; во всех остальных случаях — в v2.2. В v2.2 пустое слово уходит как `null`, чтобы сгенерированный `apiV22FilmsGet` не отправлял `keyword=`.

Ответ прокси на v2.1 нестабилен: часть запросов висит дольше клиентского `receiveTimeout` (10 с в `lib/app/api/dio_api_client.dart`), другой запрос вернул `400` с телом `{"message":"Status code '-1' should be a three-digit positive integer"}`. Например, `keyword=паук` не отвечает больше 40 секунд, а `матрица` и `Дюна` — 0,8 с. Поэтому v2.1 не единственный путь: если он бросил `RemoteDataSourceException` или вернул пустой список, тем же словом ищет v2.2 (`keyword=`), который на тех же запросах отвечает за 0,7 с.

## Последствия

- «Показать» без единого фильтра снова отдаёт подборку v2.2 без параметров; ручной поиск по строке по-прежнему идёт в v2.1.
- Если v2.1 не ответил или вернул пустой список, поиск по слову повторяется через v2.2, поэтому зависание прокси на отдельных запросах больше не даёт пустой экран.
- Цена резерва: при недоступном v2.1 экран ждёт `receiveTimeout` (10 с), и только потом показывает результаты v2.2. Таймаут задан один на всё приложение в `lib/app/api/dio_api_client.dart`, отдельного короткого таймаута для v2.1 нет.
- Ключевое слово вместе с фильтрами обслуживает v2.2: он принимает оба параметра, тогда как v2.1 фильтров не знает.
- Пробельное слово в поисковой строке (`'   '`) больше не превращается в запрос без совпадений.
- Регрессия закрыта тестом [`searched_films_bloc_test.dart`](../../test/presentation/bloc/searched_films_bloc_test.dart): он проверяет выбор эндпоинта для пустых фильтров, ключевого слова, одного фильтра, пустого списка стран и пары «слово + фильтры», а также оба случая резерва — ошибку v2.1 и его пустой ответ.
- Если появится третий сценарий с другим источником (например, коллекции переедут в это же событие), развилку придётся заменить вариантом 2 или 3.

## Отклонённые альтернативы

- **Явный `searchMode` в событии** — надёжнее при росте числа входов, но требует правки маршрута, экранов и события ради двух сценариев; развилка по `keyword` выводится из данных, которые в событии и так есть.
- **Отдельные события `SearchByKeyword` и `SearchByFilters`** — семантически чище и убирает условную логику из `_fetchFilms`, но оба экрана пришлось бы править вместе с маршрутом; выигрыш не оправдывает объём правки, пока входов два.
