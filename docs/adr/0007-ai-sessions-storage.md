# 0007. Сессии AI-Ассистента — в Hive, постеры — файлами в папке сессии

- **Статус:** Принято
- **Дата:** 2026-11-18
- **Спека:** `.scratch/ai-sessions/spec.md`

## Контекст

Экран AI-Ассистента жил одним визитом: `AiAssistantBloc` — `registerFactory`, лента поисков умирала при `pop`, а `GLOSSARY.md` прямо фиксировал «персистентность — отдельная итерация». Пользователь попросил сохранять сессии в локальное хранилище: при перезаходе, в том числе без интернета, показывать историю промптов и рекомендованных фильмов с постерами.

Сессия — диалог с моделью; сейчас в ней один ход (промпт + рекомендации), но модель данных сразу рассчитана на несколько ходов: в будущем подключается модель, умеющая вести диалог.

Вопрос — где хранить. В приложении уже есть Hive как БД (`userModelBox`, `collectionModelBox`, `filmDetailModelBox`, `filmCollectionLinkBox`, typeId 0–4) и файловое хранилище постеров (`ImageStorageService`, `images/films/<filmId>/poster.jpg`).

Варианты:

1. Hive хранит только индекс, данные каждой сессии — отдельными JSON-файлами на диске.
2. Hive хранит всё структурированное (сессия, ходы, снимки фильмов), на диске только постеры — как библиотека.
3. Гибрид: сессии и ходы в Hive, фильмы — файлами.

## Решение

Принят вариант 2.

`AiSessionModel` (typeId 5) лежит в боксе `aiSessionModelBox` с ключом `int`; внутри — `turns: List<AiSessionTurnModel>` (typeId 6), в каждом ходе — `films: List<AiFilmSnapshotModel>` (typeId 7). Снимок фильма — компактный набор полей карточки (`kinopoiskId`, `nameRu`, `nameOriginal`, `year`, `genres`, `ratingKinopoisk`, `description`), а не `FilmEntity`: сессия не должна разрастаться вместе с доменной моделью и зависеть от её будущих полей.

Постеры — файлами: `images/sessions/<sessionId>/<kinopoiskId>/poster.jpg`, в Hive хранится относительный путь (`posterPath`). Если постер не скачался, снимок сохраняется с `posterPath = null`, карточка показывает плейсхолдер и никогда не догружает постер позже — так нет второго сценария «открыли офлайн / открыли онлайн».

Сессия — снимок, а не продолжение: продолжить диалог из истории нельзя, «Повторить» из истории отсутствует. id сессии — секунды от epoch (`createdAt.millisecondsSinceEpoch ~/ 1000`, с инкрементом при коллизии): Hive принимает int-ключи только до `0xFFFFFFFF`, миллисекунды в этот диапазон не помещаются. Лимит — 20 сессий, вытесняется самая старая по `updatedAt`. Ошибки не сохраняются: сессия пишется только после валидного ответа (`loaded`/`empty`).

Запись версионируется полем `schemaVersion` внутри модели; общий `AppConfig.localStorageVersion` и `ExportDataModel` не меняются — сессии в экспорт не входят. Удаление — `box.delete` + удаление папки сессии; очистка — `box.clear` + удаление всех папок сессий.

## Последствия

**Плюс:**

- история доступна офлайн: все данные карточки — в Hive, постеры — локальные файлы;
- один механизм хранения с библиотекой: тот же Hive, тот же принцип «структура в боксе, картинки файлами»;
- модель сразу многодходовая: будущий диалог не потребует менять формат хода;
- снимок фильма изолирует сессии от эволюции `FilmEntity`;
- ошибки и недокачанные постеры не создают состояний, которые надо чинить при открытии.

**Минус:**

- постеры сессий не участвуют в экспорте и в `copyAllImagesTo` — данные уезжают без картинок;
- лимит 20 и вытеснение по `updatedAt` — продуктовая эвристика, которую придётся пересматривать, если появится «избранное»;
- снимок фильма дублирует поля `FilmEntity`: новое поле карточки надо не забыть добавить и в снимок;
- плейсхолдер вместо постера не чинится сам — пользователь видит серую заглушку, пока не удалит сессию.

## Отклонённые альтернативы

- **Hive-индекс + JSON-файлы.** Больше кода и два источника правды; Hive и так используется как БД, а JSON пришлось бы версионировать отдельно от бокса.
- **Гибрид: сессии в Hive, фильмы файлами.** Дублирует раскладку библиотеки и плодит мелкие файлы на каждый фильм; снимок в Hive дешевле.
- **Хранить `FilmEntity` целиком.** Тянет 50 nullable-полей и миграции при каждом изменении домена.
- **Хранить `posterUrl` и догружать постер при открытии.** Второй сценарий (онлайн/офлайн) и мигание плейсхолдера; выбрано «плейсхолдер навсегда».
- **`watch()` бокса для ленты.** BLoC — единственный писатель, поэтому достаточно читать при входе и обновлять состояние после save/delete; watch дал бы эхо собственных записей и гонки.
