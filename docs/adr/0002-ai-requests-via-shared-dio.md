# 0002. AI-запросы идут через общий `DioApiClient`

- **Статус:** Принято (осознанный компромисс по приватности)
- **Дата:** 2026-11-09

## Контекст

AI-воркер живёт на отдельном домене: `https://ai-movie-assistant.vladislav-vaganov-dev.workers.dev/`, эндпоинт `POST /`. Это первый POST в приложении: остальной транспорт — сгенерированный `FilmsApi` поверх `Dio`.

В приложении уже есть singleton `DioApiClient` (`lib/app/api/dio_api_client.dart`) с `baseUrl` кинопрокси, таймаутами 10 с и `InterceptorsWrapper`, который добавляет заголовок `X-User-Api-Key` (ключ пользователя Кинопоиска) **к каждому** запросу.

Варианты:

1. Переиспользовать `DioApiClient`, передав в `dio.post` полный абсолютный URL.
2. Завести отдельный `Dio` без интерсептора, чтобы ключ не покидал кинопрокси.

## Решение

Вариант 1. AI-запросы идут через `getIt<DioApiClient>().dio` (в DI `Dio` уже зарегистрирован как singleton — `injection_container.dart:101`), с абсолютным URL в `dio.post`.

## Последствия

- `X-User-Api-Key` отправляется на `ai-movie-assistant.vladislav-vaganov-dev.workers.dev`, то есть стороннему для кинопрокси воркеру. Это осознанно принято: воркер сам ходит в Кинопоиск, ключ пользователя для него не секрет, а трафик идёт по HTTPS.
- Один `Dio` на приложение: общие таймауты, общий `BaseOptions`, одна точка изменения транспорта.
- Абсолютный URL переопределяет `baseUrl` — это штатное поведение `Dio`, отдельный инстанс не нужен.
- Если воркер начнёт отвергать лишний заголовок или потребуется полная изоляция ключа — возвращаемся к варианту 2, решение пересматривается отдельным ADR.

## Отклонённые альтернативы

- **Отдельный `Dio` без ключа** — чище по приватности, но плодит второй транспорт, второй набор таймаутов и второй singleton в DI ради одного эндпоинта.
